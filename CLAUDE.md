# Flip

Room layout planner. Users redraw their room as a 2D floor plan, place furniture from a catalog, and check the result in a 3D preview. Angular 22 (standalone components, signals, zoneless), plain CSS, three.js for 3D. There is no backend yet.

## Commands

```bash
npm start              # dev server, http://localhost:4200
npm test               # Vitest unit + component tests (jsdom), ~500 tests, ~12 s
npm run e2e            # Playwright against installed Chrome; starts its own server on :4321
npm run build          # production build to dist/flip
```

Run a single Vitest file with `npx ng test --watch=false --include src/app/geometry/units.spec.ts`.

## Architecture

| Folder | Role |
| --- | --- |
| `src/app/model` | Document types (`plan.model.ts`), furniture catalog data (`catalog.ts`), 2D furniture drawings (`furniture-symbols.ts`), paint swatches, floor materials and room color schemes (`palettes.ts`), starter plans (`defaults.ts`), uploaded-model metadata (`custom-model.ts`), uploaded art images and their header parsing (`art-image.ts`), and **`plan-operations.ts`**: the pure edits UI code applies to a plan draft. |
| `src/app/geometry` | Pure math with no Angular: units, vectors, snapping, the wall graph (`wall-geometry.ts`), room detection and wall faces, furniture snapping and overlap, heights of items off the floor (`elevation.ts`), snapping on a wall face (`elevation-snap.ts`), splitting a wall around its openings plus trim sizes (`wall-pieces.ts`), walk-through start point and wall collision (`walk.ts`), and 2D viewport math (`viewport.ts`). |
| `src/app/commands` | Pure (no Angular): the command system AIs and scripts use to edit a plan. `plan-commands.ts` is the registry (`PLAN_COMMANDS`: get_plan, list_catalog, list_palettes, check_layout, add_room, add_wall, update_wall, add_opening, place_furniture, hang_on_wall, set_room and so on), `schema.ts` is a small JSON Schema subset that both describes arguments to the AI and validates them, and `run-command.ts` has `runCommand(draft, call, ctx)` and `commandSpecs()`. `CommandContext` carries what is not in the plan, the user's uploaded models and art images, which `ConsultSession` fills from `ModelLibrary` and `ImageLibrary` (`list_uploads`, `set_furniture_model`, `set_furniture_art`). |
| `src/app/state` | `PlanStore` holds the document, undo/redo and derived rooms and segments. `EditorStore` holds UI state: tool, selection, viewport, canvas size, overlay and view mode. `EditorActions` holds selection-aware commands: place, delete, duplicate, rotate and nudge. |
| `src/app/persistence` | `plan-repository.ts` holds only the `PlanRepository` contract and the `PLAN_REPOSITORY` token. `LocalPlanRepository` uses localStorage. `plan-migration.ts` validates and upgrades documents. `PlanFileService` handles JSON import/export. Uploaded 3D models: `model-repository.ts` (`ModelRepository`, `MODEL_REPOSITORY`), `IndexedDbModelRepository`, `MemoryModelRepository` (fallback and tests) and `ModelLibrary` (signal of model metadata plus cached bytes). Art images mirror that: `image-repository.ts` (`ImageRepository`, `IMAGE_REPOSITORY`), `IndexedDbImageRepository`, `MemoryImageRepository` and `ImageLibrary` (adds object URLs for the page). `idb.ts` is the shared IndexedDB file database. |
| `src/app/consult` | The AI consultant, no UI. `ai-provider.ts` is the neutral contract (`AiProvider.send`), with `anthropic-provider.ts` and `openai-provider.ts` (any OpenAI-compatible server) as adapters. `AiSettings` keeps the service, model and key in localStorage (`flip.ai`). `ConsultSession` runs the chat loop, applies edits to the plan and tracks the proposal. Providers stream (`sse.ts`) and report `AiStreamEvent`s (`text`, `thinking`, `tool`) through `AiRequest.onEvent`; the session shows them live in the chat along with a status line and elapsed seconds. Thinking is a reasoning summary and only the OpenAI Responses API gives one (Claude's extended thinking is not requested yet). `window-api.ts` publishes `window.flip` (`commands`, `run`, `runBatch`, `snapshot`). `snapshot.ts` holds the screenshot contract (`PlanSnapshotter`, the `PLAN_SNAPSHOT` token, and the `view_plan` tool spec, which is handled by the session because it needs a renderer, not by `commands/`); `history.ts` keeps only the latest screenshot in the history sent to the model. `AiSettings.screenshots` (`off`, `corner` by default, or `all`, chosen in the chat box) decides which views `view_plan` offers, so layout-only work can skip screenshots and text-only models can turn them off. `system-prompt.ts` is the instruction text. |
| `src/app/editor` | `editor-page/` is the page shell. `canvas/` holds `PlanCanvas` (input and wiring) and `view-models.ts` (pure template data). `tools/` holds the tools plus `createTools`. `properties/` holds a thin `PropertiesPanel` and one component per selection kind. `toolbox/` (the icon rail: drawing tools pinned on top, then one panel per rail tab, chosen by `EditorStore.panel`), `model-library/` (the Models panel) and `rooms/` (the Rooms panel). `elevation/` is the wall elevation view (`WallElevation` plus pure `elevation-view-models.ts`). `model-upload/` is the 3D model upload/edit dialog. `consult/` is the Consult rail tab (`ConsultPanel`). `shortcuts.ts` is the keymap and help, `autosave.ts` is the page-scoped saver, `drag-drop.ts` is the catalog drag type. |
| `src/app/preview3d` | `Preview3d` is the component. `preview-engine.ts` (renderer, camera, controls; loaded by dynamic `import()` only). `scene-builder.ts` builds the plan's three.js objects, renderer-free and testable. `model-fit.ts` stretches an uploaded model into an item's box, `model-cache.ts` parses glTF and caches by id, `model-preview.ts` is the upload dialog's lazy 3D view. `model-render.ts` renders a model's plan top view and thumbnail off screen. `plan-snapshot.ts` renders the plan once off screen (top or corner view, with labels) for the AI's `view_plan`; the editor page provides it lazily through `editor/plan-snapshotter.ts`. `texture-cache.ts` decodes art images, `floor-textures.ts` generates floor patterns. `scene-picking.ts` tags furniture, doors and windows with the `SelectionItem` they stand for (`userData.pick`; walls and floors are deliberately not clickable in 3D), resolves raycast hits for click-to-select, and draws selection outlines. `cutaway.ts` and `furniture-meshes.ts` hold the rest. |
| `src/app/shared` | Reusable UI and helpers: `FurnitureSymbol` (SVG `g[appFurnitureSymbol]`), `ColorSwatches`, `LengthInput`, `Icon`, `PlanThumbnail`, `color.ts` (`shade`), `base64.ts` and `dom.ts` (`isTypingTarget`, `focusWhileOpen` for dialogs). |
| `src/app/projects` | The project list page. |
| `src/app/testing` | Test-only fixtures, including `glb.ts` (`boxGlb()`, a generated GLB used by unit and e2e tests). App code must never import them. |

Dependency direction: `model`, `geometry` and `commands` (pure) ← `state` ← `consult`, `editor`, `projects` and `preview3d`. `editor` may import `consult`, never the reverse. Lower layers never import from `editor`.

Routes: `/` shows the projects page and `/plan/:id` opens the editor. Both are lazy.

## Conventions and invariants

- **Units:** store all lengths in centimeters and all angles in degrees. Feet and inches are display only, through `formatLength`, `parseLength` and `formatArea` in `geometry/units.ts`. Plan coordinates are y-down. In 3D, plan (x, y) maps to (X, Z) in meters.
- **Editing the document:** always go through `PlanStore.update(draft => ...)`. It deep-clones the plan, so mutating the draft is fine. Put any edit that has rules, such as clamping, normalizing or creating metadata, in `model/plan-operations.ts` (or `wall-geometry.ts` for wall-graph changes), and call it from the UI. Do not write the rule inline in a component. Pass `{ coalesceKey }` for continuous gestures such as drags and nudges, then call `commit()` when the gesture ends, so the whole gesture is one undo step.
- **Walls:** walls share `WallNode`s, so use the helpers in `wall-geometry.ts`: `addWall`, `splitWall`, `mergeNodes`, `removeWalls` and `reclampOpenings`. `addWall` splits existing walls at T-junctions and crossings. Room detection assumes walls meet only at shared nodes.
- **Accent walls:** each face of a wall can carry its own paint in the optional `Wall.colors` field (`{ front?, back? }`). `front` is the face on the side the wall's normal (`perp(b - a)`) points to. A face without an accent uses the wall color of the room on that side. Use `roomsBesideWall` and `wallFaceColor` from `geometry/room-detection.ts` instead of re-deriving sides. `splitWall` copies the colors onto both pieces.
- **Wall types:** `Wall.type` is unset for a solid wall, `railing` for an open 36" railing (`RAILING` and `railingParts` in `geometry/wall-pieces.ts`), or `hidden` for an invisible room divider that builds nothing in 3D. Both still bound rooms and keep `height`, because a room's ceiling is its tallest wall. Neither gets accent paint, trim or openings in 3D. Set it with `setWallType`.
- **Rooms:** rooms are derived from the wall graph and never stored. `RoomMeta` (name and colors) attaches by an anchor point inside the room. A selected room is identified by its `key`, which is the sorted wall ids, so the key changes when its walls are split.
- **Thin components:** `PlanCanvas` only wires signals to the builders in `canvas/view-models.ts` and handles input. Each properties section is its own component. New canvas visuals get a pure builder plus a spec. New panel sections get their own component that uses `properties.css`.
- **Shortcuts:** add or change keys only in `editor/shortcuts.ts`. The help dialog renders from the same table, and `shortcuts.spec.ts` rejects duplicate bindings.
- **Furniture drawing:** use `<g appFurnitureSymbol>` anywhere a furniture symbol appears. Do not re-implement `symbolParts` rendering. Colors and swatches come from `model/palettes.ts`. Use `ColorSwatches` for any swatch row.
- **Tools:** tools implement `Tool` in `editor/tools/tool.ts`. They receive world coordinates and a `hit`, which the canvas reads from `data-kind`, `data-id` and `data-handle` attributes on SVG elements. A tool's `onKeyDown` runs before the global shortcuts in `EditorPage.onKeyDown`, and returning true consumes the key.
- **Uploaded 3D models:** a model is a *variant* of a catalog template (`CustomModel.catalogId`). A placed item keeps its own `catalogId`, size and 2D symbol, and `FurnitureItem.modelId` only swaps its 3D look; the model is stretched per axis to the item's box (`fitModelToBox`) after the model's quarter-turn `orientation`. An optional `CustomModel.trim` cuts fractions (max 45% per side) off the model's measured bounds first, for files with empty space or stray parts; trimmed-off geometry sticks out of the box. Models live in `MODEL_REPOSITORY` (IndexedDB), never in the plan; a missing model falls back to the built-in primitive and keeps the `modelId`. Each model also has rendered pictures (`ModelRenders`: a PNG top view framed exactly on the fitted box, which the 2D plan stretches over the item through `FurnitureSymbol`'s `topView`, and a thumbnail for the catalog and Models panel). They are stored beside the file (the `renders` store, database version 2), are tagged with `modelRenderKey` (file, template size, orientation, trim, colors), and are redrawn by `ModelRenderQueue` (`editor/model-render-queue.ts`, provided by `EditorPage`, rendering with `preview3d/model-render.ts`) whenever a model's key no longer matches. That one path covers uploads, edits, imports and models uploaded before pictures existed. `CustomModel.planSymbol` keeps the template's symbol on the plan instead. Pictures are not exported. Plan export embeds used models as base64 under `models`; import restores them and remaps ids on a clash. Fitted instances share geometry with `ModelCache`, so `disposePlanScene` skips meshes tagged `SHARED_MODEL`. Only .glb and self-contained .gltf are read so far.
- **Heights and mounts:** a catalog item's `mount` is `floor` (default), `wall` or `ceiling`. `FurnitureItem.elevation` is the bottom of the item above the floor; always read heights through `itemElevation`, because ceiling items ignore `elevation` and hang at the ceiling minus their height (their Height is the drop). `stackable` items rest on the floor item under their center (`restingElevation`) when placed or dragged, and dragging a base carries them (`itemsRestingOn`). A wall item hangs on the face its back is flush against (`mountedWall`); move it with `moveOnWall`. `findOverlaps` ignores pairs at different heights. A room's ceiling height is the height of its tallest wall; `setRoomCeilingHeight` sets all of its walls, so there is no stored ceiling field.
- **Room finishes:** `RoomMeta` has optional `ceilingColor`, `trimColor`, `floorMaterial` and `crownMolding`; `attachRoomMeta` fills defaults from `palettes.ts`. A color scheme (`ROOM_SCHEMES`) is applied as one `upsertRoomMeta` patch and is recognized by comparing finishes (`matchingScheme`), not stored. Trim sizes live in `geometry/wall-pieces.ts` for both the 3D trim and the elevation drawing.
- **Art images:** `FurnitureItem.artImageId` points at an image in `IMAGE_REPOSITORY` (its own IndexedDB database, `flip-images`), never in the plan. A missing image falls back to a plain picture. Export embeds used images under `images` and import remaps clashing ids, through the same code as models. Image type and size come from the file header (`readImageHeader`), so no decoding is needed outside the 3D view.
- **Walk mode:** the Walk button in `Preview3d` calls `PreviewEngine.startWalk` (camera at `WALK_EYE_HEIGHT`, orbit controls off, cutaway off). Keys are captured on `window` while walking, so W, D and the arrows never reach the editor shortcuts; Esc leaves. Collision is pure math in `geometry/walk.ts`: obstacles come from `wallPieces`, so doorways are open and window sills block, railings block and hidden walls do not. Furniture does not block yet, and the 2D plan does not show where the visitor stands.
- **Sidebar:** the left sidebar (rail plus panel) is resizable by the divider in `EditorPage`; `state/sidebar-width.ts` clamps the width and saves it in localStorage (`flip.sidebarWidth`), and the layout reads it through the `--sidebar-width` CSS variable. New tools or catalog-like features get a rail tab, not a new dialog.
- **Elevation view:** `EditorStore.elevation` holds the open wall face and replaces the 3D preview beside the plan; closing it returns to the current view mode. Its drawing frame puts x along the face as seen from that side (`+dir` for the front, `-dir` for the back; see `faceFrame`) and y = -height. Keys go to `WallElevation.handleKey` before the canvas and global shortcuts.
- **Dialogs:** use the shared `.modal-backdrop` / `.modal` styles, call `focusWhileOpen` and stop `keydown` propagation in the dialog, so Escape and editor shortcuts never reach the plan behind it.
- **AI commands:** every way an AI changes a plan is a `Command` in `commands/plan-commands.ts`: a snake_case name, a description, a JSON Schema for its arguments, and a `run(draft, args)` that builds on `plan-operations.ts` and `wall-geometry.ts` (never writes its own rules). A command checks everything before it changes anything and throws `CommandError` for a request it cannot carry out; the message goes back to the AI. Lengths are centimeters and angles degrees. To add a capability, add a command and a case in `run-command.spec.ts`; providers, the chat and `window.flip` pick it up with no other change.
- **Consult and proposals:** all AI edits go through `ConsultSession.execute`, which applies them to the open plan with one `coalesceKey`, so a proposal is one undo step. The user sees the changes live and picks Keep or Discard (Discard is `undo()` and is only offered while the plan's revision still matches the proposal's). Read-only commands never touch the plan. `ConsultSession` is provided by `EditorPage`, so each plan gets a fresh conversation. To support another AI service, implement `AiProvider` and add it in `AiSettings.createProvider`. Other agents in the page can call `window.flip.commands()`, `.run(name, args)` and `.runBatch(calls)`, which use the same path. API keys live only in this browser's localStorage and requests go straight from the browser to the service.
- **Storage:** keep storage behind `PLAN_REPOSITORY`. User accounts are planned, and a server repository should be a drop-in replacement. Bump `CURRENT_SCHEMA_VERSION` and extend `migratePlan` in `plan-migration.ts` for any incompatible change to the document format. Optional new fields need no bump.
- **Bundle size:** three.js must stay in a lazy chunk. Never import `preview-engine`, `scene-builder`, `furniture-meshes` or `three` statically from code reachable without the 3D view. The initial bundle is about 250 kB.
- **Styles:** the component style budget is 10 kB (warning) and 20 kB (error). Shared button, input and segmented styles live in `src/styles.css`.

## Testing notes

- **Tools:** test tools by calling `onPointerDown`, `onPointerMove`, `onPointerUp` and `onKeyDown` directly. Use `pointer()`, `toolContext()`, `squareRoom()` and `key()` from `src/app/testing/fixtures.ts`.
- **jsdom gaps:** jsdom has no `ResizeObserver`, so call `installResizeObserver()` before creating `PlanCanvas` or `EditorPage`. It also has no WebGL, so `EditorPage` specs replace `Preview3d` with a fake component.
- **Zoneless rendering:** after dispatching DOM events in component specs, call `fixture.detectChanges()`, because the browser would run change detection there. Promises that `whenStable` does not track need an `await new Promise(r => setTimeout(r))`.
- **E2E:** every e2e test fails on any console error, through the auto fixture in `e2e/helpers.ts`. Use web-first assertions instead of fixed waits. Use `savedPlan(page, predicate)` to read the stored plan, because it polls until autosave catches up.
